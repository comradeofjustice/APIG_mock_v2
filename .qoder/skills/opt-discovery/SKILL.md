# Discovery（前置研究）

AI 在研究中的角色是**合成器，而不是采集器**。只处理人提供的原材料，不虚构用户数据或竞品体验。没有数据前提的子工具直接跳过。

> **输出原则**：三类研究各自执行完成后，**对话只输出最终汇总文件的 Handoff 摘要**。中间工具调用、分析过程、草稿内容**一律不在对话中展示**，直接写文件。

---

## 核心原则

> **不造数据**：亲和图需要真实的访谈/反馈原文；竞品分析需要用户提供竞品名称。AI 基于训练知识生成的内容（如竞品功能推断、趋势摘要）会明确标注"基于 AI 知识，建议实际验证"。

---

## 研究类型分类

```
┌─ A. 竞品分析类（完整竞品分析 + 趋势分析，按数据前提触发）
│     竞品分析 / 趋势分析
│     产出合并写入：competitive-analysis.md（含趋势分析节）
│
├─ B. 文档解析类（需用户提供文档）
│     投标参数分析 / 合规要求分析
│     产出：tender-analysis.md / compliance-gap-analysis.md
│
└─ C. 洞察研究类（需用户数据或明确场景）
      亲和图 / 用户画像 / 用户旅程图
      产出：affinity-diagram.md / personas.md / customer-journey-map.md
```

三类可组合叠加，每类内部的子工具独立检查数据前提、可部分执行。

---

## 子工具及触发条件

**A 类 — 竞品分析类**

| 子工具 | 触发前提 | 无前提时 | 输出文件 |
|---|---|---|---|
| 一、竞品分析 | 用户能说出竞品名称；安全领域自动委托 cybersecurity-competitive-research 真实爬取 | 跳过 | `competitive-analysis.md` |
| 二、趋势分析 | 新赛道 / 有明确技术转型背景，或用户明确要求 | 跳过 | 追加写入 `competitive-analysis.md` 的「趋势分析」节 |

**B 类 — 文档解析类**

| 子工具 | 触发前提 | 无前提时 | 输出文件 |
|---|---|---|---|
| 三、投标参数分析 | 用户提供投标文档（文件路径 / 粘贴文本 / URL） | 跳过，提示用户提供文档 | `tender-analysis.md` |
| 四、合规要求分析 | 用户提供标准文档，或说明具体标准名称（等保/GDPR/SOC 2 等） | 跳过，提示用户提供标准依据 | `compliance-gap-analysis.md` |

**C 类 — 洞察研究类**

| 子工具 | 触发前提 | 无前提时 | 输出文件 |
|---|---|---|---|
| 五、亲和图 | 用户提供原始访谈摘录/痛点原文 | 跳过（不虚构数据） | `affinity-diagram.md` |
| 六、用户画像 | 角色尚不明确，或用户明确要求 | 降级为 Stage 1 轻量角色定义 | `personas.md` |
| 七、旅程图 | 路径跨越系统边界（使用前/使用中/使用后） | Stage 1 Story Script 已够用 | `customer-journey-map.md` |

## 执行流程

```
0. 语境预判：根据用户输入判断研究类型是否已明确
   - 已明确（如"做竞品分析"/ "投标文件分析" / "合规分析" / "用户画像"）
     → 跳过步骤 1，直接进入步骤 2，只对对应类别的子工具检查前提
   - 不明确 → 进入步骤 1

1. 调用 AskQuestion 工具，呈现结构化多选题：

   标题：本次前置研究要执行哪些类型？
   allow_multiple: true
   选项：
     a - A 类：竞品分析（完整竞品分析 + 趋势分析，默认真实爬取 / 网络受限时降级为 AI 知识路径）
     b - B 类：文档解析（投标参数分析 / 合规要求分析，需提供文档）
     c - C 类：洞察研究（亲和图 / 用户画像 / 旅程图，需提供原始数据或明确场景）

   等待用户回复后再继续：
     仅选 a → 只执行 A 类子工具（一～二）
     仅选 b → 只执行 B 类子工具（三～四）
     仅选 c → 只执行 C 类子工具（五～七）
     多选组合 → 执行所选类别的对应子工具

2. 对所选类别内的各子工具逐一检查数据前提
3. 确认哪些子工具有前提可执行（不在对话中逐项展示检查过程）
4. 静默执行有前提的子工具，将所有结果直接写入对应文件（不在对话展示中间结果）
5. 输出最终 Handoff → Stage 1（格式见下方"对话中呈现的内容"）
```

## 子工具一：竞品分析（Competitive Analysis）

### 前提检查

```
用户是否提供了竞品名称？
  是 → 执行
  否，且行业内有知名产品 → 主动列出候选，用户确认后执行
  否，且是内部工具/无竞品 → 跳过，在摘要中注明"无竞品参照"
```

### 执行路由（执行前判断）

```
默认路径（所有领域）：
  → 读取 ~/.cursor/skills/opt-cybersecurity-competitive-research/SKILL.md
  → 按其四步流程执行真实网络爬取（官网 → B站/YouTube → Behance/Dribbble → 更新报告）
  → 产出含真实链接的 competitive-analysis.md

降级为 AI 知识路径（仅当满足以下条件之一时）：
  - 用户明确说"快速分析"/"不需要真实链接"/"仅需摘要"
  - WebFetch / WebSearch 连续失败（网络受限）
  → 走 AI 知识路径（见下方执行步骤），内容标注"基于 AI 知识，建议实际验证"
```

### AI 知识路径执行步骤（降级备用）

1. 收集竞品名称（用户提供 or AI 推荐后用户确认）
2. 从以下维度生成对比矩阵（基于 AI 训练知识，标注置信度）
3. 提炼差异化机会点

### 分析维度

| 维度 | 说明 |
|---|---|
| 核心功能覆盖 | 列出目标功能点，逐产品标注支持/不支持/部分支持 |
| UX 模式 | 列表/卡片/看板；筛选位置；操作区设计 |
| 信息架构 | 导航层级；功能入口深度 |
| 状态管理 | 草稿/发布/归档 等生命周期设计 |
| 差异化亮点 | 竞品的特色功能或体验优势 |
| 已知缺陷 | 用户反馈中的痛点（如有公开数据） |

### 输出格式（写入 `competitive-analysis.md`，AI 知识路径）

```markdown
# 竞品分析 — {模块名}

> 数据来源：AI 训练知识 + 公开资料。功能状态建议实际操作验证。

## 分析范围
- 目标功能：{本次设计的核心功能点}
- 对标产品：{竞品列表}

## 功能对比矩阵

| 功能点 | 本产品 | 竞品 A | 竞品 B | 竞品 C |
|---|---|---|---|---|
| ... | 待定 | ✓ | ✗ | △（部分） |

## UX 模式对比

| 维度 | 竞品 A | 竞品 B | 竞品 C |
|---|---|---|---|

## 差异化机会点

1. {机会点描述} — 当前竞品的不足或空白
2. ...

## 结论与建议
{2-3句：我们应该参考什么，回避什么，可以做什么差异化}
```

## 子工具三：投标参数分析（Tender Analysis）

### 前提检查

```
用户是否已提供投标文档？（支持三种输入方式）
  文件路径（PDF/Word/TXT）→ 使用 Read 工具读取
  粘贴文本 → 直接处理
  URL → 使用 WebFetch 工具抓取
  否 → 跳过，并提示：
       "投标参数分析需要招标文件作为输入。
        请提供文档路径、URL 或直接粘贴需求条目后重新触发此工具。"
```

### 执行步骤

1. **解析文档** — 提取所有需求条目，按类别分组：
   - 功能性需求
   - 非功能性需求（性能 / 可用性 / 安全）
   - 合规与集成要求
   - 交付物要求

2. **读取功能基线** — `Read project_description.md`（若存在）；同时扫描 `docs/ux/*/prd.md` 作为已有功能补充；不存在则询问用户描述当前产品能力。

3. **逐条对比** — 对每个需求条目评定状态：
   - `✓ 已有` — 当前产品完整覆盖，标注覆盖来源（哪个 PRD 文件）
   - `△ 部分满足` — 有基础能力但存在缺口，说明具体差距
   - `✗ 缺失` — 当前产品无此能力

4. **生成优先级建议** — 按投标得分权重 × 实现难度排序，输出 Top 5 待补充项。

### 输出格式（写入 `tender-analysis.md`）

```markdown
# 投标参数分析 — {模块名/项目名}

> 基于提供文档解析，功能基线来自 project_description.md 及已有 PRD 文件。
> 建议结合实际开发状态人工核对"部分满足"和"缺失"条目。

## 文档来源

- 解析日期：{日期}
- 基线版本：project_description.md + {N} 个 PRD 文件
```

## 子工具四：合规要求分析（Compliance Gap Analysis）

### 前提检查

```
满足以下任一条件才执行：
  - 用户提供了标准文档（路径 / 粘贴文本 / URL）
  - 用户说明了具体标准名称（等保 2.0 / GDPR / SOC 2 / ISO 27001 / 行业规范等）
    → 基于 AI 训练知识提取标准条目，标注"基于 AI 知识，建议对照正式文档验证"
否则 → 跳过，并提示：
       "合规要求分析需要指定标准名称或提供标准文档。
        请说明适用的合规标准（如等保 2.0、GDPR）后重新触发此工具。"
```

### 执行步骤

1. **获取标准条目** — 若用户提供文档则解析；若仅说明标准名称则基于 AI 知识提取关键条款，并标注置信度。

2. **读取功能基线** — `Read project_description.md`（若存在）；同时扫描 `docs/ux/*/prd.md` 了解已有功能设计；不存在则询问用户补充描述。

3. **逐条对标** — 对每个合规条款评定状态：
   - `✓ 已满足` — 当前设计/实现已覆盖
   - `△ 部分满足` — 有一定覆盖但存在缺口，说明具体差距
   - `✗ 缺失` — 当前产品无对应设计
   - `N/A` — 该条款不适用于本产品

4. **生成设计/开发建议** — 针对"缺失"和"部分满足"项，提出对应的设计方向或功能要求，可直接输入 Stage 2 PRD。

### 输出格式（写入 `compliance-gap-analysis.md`）

```markdown
# 合规要求分析 — {模块名/项目名}

> 标准来源：{文档名称 / AI 知识（建议对照正式文档验证）}
> 功能基线：project_description.md + {N} 个 PRD 文件

## 适用标准
- 标准名称：{等保 2.0 / GDPR / SOC 2 / ...}
- 适用范围：{哪些功能模块 / 数据类型受此标准约束}

---

| 条款编号 | 条款描述 | 当前状态 | 差距说明 | 设计/开发建议 |
```
