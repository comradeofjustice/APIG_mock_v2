一、背景与问题定义
1.1 业务背景
API安全网关系统中，大部分客户使用的是直接操作模式：

API / 服务 / 策略配置 → 直接生效

但存在一小部分高安全客户 / 合规客户需要：

所有敏感操作必须经过审批后才能生效

1.2 核心特点
✔ 配置型系统（非交易/非高频）
✔ 写少读多
✔ 强一致性要求低（最终一致）
✔ 审批是“增强能力”，不是核心功能
✔ 默认90%客户不启用审批
同一个 resource_id + operation_code + in_progress 重复提交这个由程序判断。重复直接不让审批单提交。
我的系统审批执行失败。需要找开发人员定位问题。不涉及重复提交机制
execution_status不再前端展示。仅在开发人员定位执行失败问题时使用

二、核心设计目标
保证配置变更可控
审批能力可插拔
不影响原有业务代码
保持执行链路稳定
支持用户上下文全链路传递

五、审批流程设计
5.1 流程状态驱动
待审批 → 审批中 → 已通过 → 已执行
↓
已拒绝

5.2 状态模型设计
系统采用“双阶段状态模型”：

阶段一：审批态（审批流程控制）

- status 表示审批进度

阶段二：执行态（业务执行结果）

- execution_status 表示审批通过后的执行结果

类型	字段	说明
审批状态	status	控制审批流转
执行状态	execution_status	控制业务执行结果
5.3 状态不可逆规则
状态不可逆原则：

1. approved 不代表 success
2. success 只能由 service 执行结果产生
3. failed 不允许自动重试覆盖为 success
4. execution_status 为最终事实状态

5.4 审批通过约束
执行流程必须串行：

1. 审批通过事务提交完成后立即执行
2. 执行过程必须阻塞当前线程
3. service 执行结果直接决定状态更新

failed 状态说明：

- 表示业务执行失败
- 不影响审批状态（审批仍为 approved）
- 必须保留用于问题排查与人工修复

六、执行触发机制
正确机制：审批通过即触发执行,审批通过后必须同步执行：

审批人点击通过
↓
ApprovalService.update(status=APPROVED)

↓

写入 t_approval_record（记录审批动作）
↓
事务提交成功
↓
立即调用 ExecutionDispatcher（同步阻塞，同步执行必须设置超时控制（例如 30s / 60s））
↓
执行 service
↓
根据执行结果更新 execution_status
↓
返回最终结果

九、PG数据库设计
9.1  核心设计原则
本次审批系统数据库设计遵循以下原则：

1. 单操作单审批模型（简单清晰）
2. 审批规则与实例解耦
3. 审批流程扁平化（不做复杂流程引擎）
4. 低并发场景下采用轻量设计
5. 预留扩展字段（snapshot等）
6. 审批规则 不合并到你现有的 t_policies_rule 表里，t_policies_rule 本质是 网关运行时策略规则表。审批规则是：管理后台“操作行为控制规则”，两者语义完全不同
7. 任务创建即完成规则绑定，形成任务级别的执行快照，任务执行期间不再依赖规则表，规则变更仅影响“新的审批单”
8. 本系统采用业务层幂等控制，不引入数据库唯一约束或分布式锁机制。

原因如下：

1. 系统为低频配置型系统
2. 审批操作允许人工兜底
3. 追求架构轻量化，避免引入复杂一致性机制
4. 极端并发情况下允许少量重复审批单，由后台人工处理

十三、接口设计文档（基于PRD+原型补充）

### 13.1 设计目标

- 本章节用于约定前后端联调接口，作为审批模块 API 契约基线。
- 接口字段命名遵循：对外 `camelCase`，数据库保持 `snake_case`。
- 涉及数据库字段时，接口语义优先与表字段含义一一对应，避免歧义。

- 接口前缀：`/api/v1/approval`
- 数据格式：`application/json`
- 鉴权：沿用现有登录态与权限体系
- 时间字段契约：
  - `createTime` / `updateTime` / `records[].createTime` 使用时间戳毫秒数（与 `LocalDateTime` 运行时序列化一致）
  - `timeline[].time` 为时间线展示字段，保持字符串时间

### 13.3 状态与动作字典

审批状态（`status`）：

- `pending`：待审批
- `in_progress`：审批中
- `approved`：已通过
- `rejected`：已拒绝
- `recalled`：已撤回

执行状态（`executionStatus`）：

- `pending`：待执行
- `executing`：执行中
- `success`：执行成功
- `failed`：执行失败

审批动作（`action`）：

- `approve`、`reject`、`recall`

> 说明：数据库字段仍为 `snake_case`（如 `execution_status`），接口字段名使用 `camelCase`（如 `executionStatus`）；状态/枚举字段值沿用业务口径（如 `in_progress`），不因字段名风格而改值。

### 13.9 原有业务接口接入审批流程（不新增触发接口）

Contract Type: `Target Design Contract`

#### 13.9.1 设计说明

- 本项目不新增独立“操作触发审批”接口。
- 审批触发逻辑接入现有业务操作接口（如 API 管理、服务管理、证书管理等原接口）。
- 前端仍调用原业务接口，审批系统作为后端流程分支处理。

#### 13.9.2 接入流程（原接口内）

1. 用户调用原业务操作接口（如新增/变更/删除）。
2. 后端根据 `moduleCode + operationCode` 查询是否命中审批规则。
3. 若未命中规则：继续原业务逻辑并返回原接口成功响应。
4. 若命中规则：
  - 创建审批任务（`status=pending`，记录 `approvalFlow`、`changeSnapshot` 等）；
  - 原业务变更暂不执行；
  - 原接口返回“已进入审批流程”的业务响应（具体文案按原模块约定）。
  - 响应口径建议：以外层 `code` 作为前端主判定字段；命中审批时返回“数字业务码”（示例：`2001`，表示已进入审批），并在 `data` 中返回 `taskId`（审批任务ID）用于前端跳转详情与状态跟踪。
  - 对历史 `Void` 写操作接口：允许保持返回类型不变，但命中审批时必须返回“数字业务码”（示例：`2001`）；若支持结构化扩展，优先补充 `data.taskId`，避免前端二次反查任务。
5. 审批通过后由审批执行链路驱动实际变更落地；审批拒绝则终止本次变更。

#### 13.9.3 与审批模块接口关系

- 原业务接口负责“触发审批或直通执行”。
- 审批管理接口负责“查询任务、审批处理、我的申请、详情查看、撤回”等能力（见 13.7/13.8）。

#### 13.9.3.1 码值归属规则（审批接入统一口径）

- 审批接入场景的“已进入审批流程”统一使用业务码 `2001`（外层 `code`）。
- `2001` 语义固定为“请求已受理并进入审批流程，原业务写入暂未执行”，禁止复用为其他语义。
- 各业务模块不得自行定义新的“审批中”业务码；若需扩展审批相关业务码，必须先登记到统一错误码/业务码表并完成评审。
- 统一错误码/业务码表至少应包含：`code`、`语义`、`适用接口范围`、`前端处理策略`、`负责人/变更记录`。
- 前端分支处理以 `code` 为准：`0` 表示直通成功，`2001` 表示进入审批，其他码按失败处理；`message` 仅用于展示。

#### 13.9.3.2 业务侧代码接入模板（强约束）

- 主流程必须“轻嵌入审批闸门”，禁止把审批细节散落在主流程内。
- 推荐固定步骤：`query beforeData -> validate -> build afterData -> tryCreateTask -> (submitted ? 返回审批中 : 执行原写入)`。
- 业务主流程中仅允许一处审批分支判断；审批规则匹配、审批人校验、互斥校验、快照组装必须下沉到审批服务。
- `currentUserId` 为空口径：默认不触发审批，按原业务直通执行（用于兼容存量未注入用户ID的接口）。
- 审批通过后的真实变更必须走独立方法（如 `applyApprovedXxx`），禁止复用“提交阶段”方法，避免重复触发审批。
- 删除/批量删除场景同样遵循统一返回口径：命中审批返回 `code=2001` + `taskId`（若可用）；直通成功返回 `code=0`。
- 历史 `Void` 写接口兼容规则：短期允许保持返回模型不变，但命中审批时必须返回 `code=2001`；中长期建议升级为可承载 `taskId` 的结构化响应。

#### 13.9.4 可执行流程契约（编码必需）

为避免“文档可读但不可编码”，本节定义接入审批后执行链路的最小可编码契约。

1. 触发入口（Trigger Entry）

- 入口：原业务操作接口（如 `/apisix/**`、`/api/v1/**` 业务写操作）。
- 判定：按 `moduleCode + operationCode` 命中审批规则。

1. 准入条件（Admission）

- 若未命中规则：直通原业务逻辑。
- 若命中规则：进入审批链路，创建审批任务并阻断原业务写入。
- 前端通知口径：统一以响应 `code` 判定是否进入审批（示例：`2001`）；`message` 仅作展示，不作为流程分支依据。

1. 持久化写入（Persistence Writes）

- 创建审批任务时必须写入以下字段：
  - `id`（任务主键，作为前端 `taskId` 回传来源）
  - `moduleCode`
  - `operationCode`
  - `resourceId`
  - `status = pending`
  - `executionStatus = pending`
  - `approvalFlow`（规则快照）
  - `changeSnapshot`（执行快照）

1. 执行快照结构（changeSnapshot）

- `changeSnapshot` 默认结构如下（最小必要字段，禁止预埋未消费字段）：

```json
{
  "resourceId": "resource_001",
  "beforeData": {},
  "afterData": {},
  "executeRequest": {
    "targetSystem": "apig-console",
    "payload": {}
  }
}
```

1. 审批通过后执行（Post-Action Execution）

- 审批通过后必须同步触发 `ExecutionDispatcher`。
- `ExecutionDispatcher` 负责：
  - 按 `moduleCode + operationCode` 路由执行器；
  - 回写 `executionStatus`（`executing/success/failed`）。

1. 跨服务调用契约（Cross-Service Contract）

- 当落地执行在外部服务（如 `apig-data-service`）时，调用请求至少包含：
  - `taskId`
  - `moduleCode`
  - `operationCode`
  - `resourceId`
  - `payload`
- 响应至少包含：
  - `success`（布尔）
  - `message`（失败原因）
  - `data`（可选执行回执）

1. 失败处理与重试（Failure Policy）

- 执行超时或异常时，统一置 `executionStatus = failed`。
- `failed` 不自动改写为 `success`。
- 本系统默认不引入自动重试机制；需重试时由人工触发“重试执行”能力（后续版本可扩展）。

1. 并发去重（Concurrency Guard）

- 创建审批任务前必须做冲突检查：
  - 条件：`moduleCode + resourceId + status in ('pending', 'in_progress')`
  - 命中即拒绝新建并返回冲突提示（不区分 `operationCode`）。
- 该规则用于避免“同资源多操作并行审批单”重复创建（如 `change` 未完成前再提 `delete`）。

1. 清单-契约对账（Reconciliation）

- 本章节“状态变更操作”采用统一流程契约，不在每个业务模块重复拷贝。
- 对账口径：
  - 业务操作清单：见第 5 章（PRD）
  - 流程契约块：本节 `13.9.4`（统一契约）
  - 状态机覆盖：第 5/6/13 章状态定义与流转
- 对账结论：采用“统一契约 + 多操作复用”模式，允许“1 契约块覆盖 N 操作”，但 N 操作均必须遵守本节约束。

| 类型字段（type）             | 对应业务语义  | `moduleCode` 取值规则                               | `operationCode`（新增/变更/删除）   |
| ---------------------- | ------- | ----------------------------------------------- | --------------------------- |
| `desensitization_rule` | 脱敏规则    | 由 `type` 推导，`moduleCode = desensitization_rule` | `add` / `change` / `delete` |
| `watermark_rule`       | 水印规则    | 由 `type` 推导，`moduleCode = watermark_rule`       | `add` / `change` / `delete` |
| `access_control`       | 访问控制    | 由 `type` 推导，`moduleCode = access_control`       | `add` / `change` / `delete` |
| `whitelist`            | 白名单     | 由 `type` 推导，`moduleCode = whitelist`            | `add` / `change` / `delete` |
| `ai_policy`            | AI 合规策略 | 由 `type` 推导，`moduleCode = ai_policy`            | `add` / `change` / `delete` |


约束说明：

- 以上映射为本项目固定口径；未显式变更文档前，代码实现不得改写。
- 策略类接口请求中 `moduleCode` 可不传，由后端按 `type` 自动推导（等值映射）。
- 若前端仍传 `moduleCode`，后端必须校验其与 `type` 推导结果一致；不一致返回参数错误。
- 若后续新增策略类型，必须先在本表补充 `type -> moduleCode -> operationCode` 映射，再允许编码。
- 版本边界声明：当前为新版本功能口径，不包含历史 `edit` 兼容要求；`operationCode` 仅允许 `add/change/delete`。

- MUST：`changeSnapshot.beforeData` 必须来自更新入口内对目标资源的实时查询结果（如 `selectById` / 主键精确查询），并以该查询结果作为唯一事实源。
- MUST：更新审批单构建顺序固定为：`先查 store(beforeData)` -> `再做 updatePreCheck` -> `再组装 afterData` -> `再创建审批单`。
- MUST：若实时查询结果为空（资源不存在），必须直接返回“资源不存在”错误并终止，不得创建审批单。
- MUST NOT：禁止使用请求体字段反推、拼装或猜测 `beforeData`。
- MUST NOT：禁止使用缓存、副本或历史快照替代实时查询结果作为 `beforeData` 主来源。
- MUST NOT：禁止在 `beforeData` 缺失关键业务字段（至少 `id/type/ruleStatus/ruleCondition/ruleAction`）时继续创建审批单。
- MUST：命中审批规则后必须执行“审批人有效性校验”（审批人存在且可用）；若任一审批人已删除/失效，则该规则本次判定为“不可用规则”并跳过匹配下一优先级规则。
- MUST：若所有候选规则都因“审批人已删除/失效”不可用，则按严格模式阻断操作并返回“无可用审批规则（审批人失效）”错误。
- MUST：同一资源审批单必须互斥（不区分操作类型）。只要存在 `status in (pending, in_progress)` 的审批单，禁止为同一 `moduleCode + resourceId` 再创建任何新审批单（包括 `change/delete/add`）。
- MUST：命中资源级互斥时，必须阻断并返回“该资源存在进行中的审批单，不允许提交新的审批操作”。
- MUST NOT：禁止在同一 `moduleCode + resourceId` 已有进行中审批单时，继续提交不同 `operationCode` 的审批请求（例如 `change` 未完成前再提 `delete`）。

### 13.10 权限、错误码与实现约束

权限约束：

- 审批规则管理（新增/变更/删除）：仅超级管理员可访问。
- 任务中心审批动作（通过/拒绝/批量审批）：仅具备审批权限用户可访问。
- 我的申请撤回：仅申请人可操作。

错误码建议：

- 参数错误：`INTERFACE_INPUT_PARAMETER_EXCEPTION`
- 非法状态流转：`OPERATION_NOT_EXECUTABLE`
- 资源冲突：返回明确 `conflictMessage`

实现约束：

- 文档字段与 DB 字段语义保持一致；展示层字段可聚合但必须有映射说明。
- 所有外部接口字段命名统一使用 `camelCase`。
- 涉及“新增/变更”且存在名称类字段（如 `ruleName`）时，默认采用“全局唯一”约束；若需改为“租户内唯一 / 启用态唯一 / 允许重名”，必须在文档中显式声明例外口径。
- 涉及复杂详情/列表返回模型（存在派生字段计算、跨表聚合、集合排序、结构拆分重组）时，默认采用“两段式实现”：Mapper 仅查询稳定基础字段，Service 负责派生补全（计算、聚合、排序、拆分）；不得在无性能瓶颈证据下将复杂派生规则直接堆叠在 SQL 中。
- 涉及分页查询且存在可选筛选字段（如 `status/moduleCode/keyword`）时，默认口径为“不传即不加该字段过滤（查全部）”；若需设置默认筛选条件，必须在对应接口章节显式声明。
- 版本兼容口径必须显式声明：若文档未声明“兼容历史版本/历史值”，实现阶段一律按“新版本纯净口径”落地，不得自行加入历史兼容逻辑。
- `operationCode` 白名单固定为 `add/change/delete`；`edit` 视为非法口径，不得在代码、SQL、示例、校验或映射中出现。
- 禁止在无明确条款时引入历史兼容分支（如 `edit <-> change` 双向映射、双写双读、兼容回退执行）；如确需兼容，必须在文档中注明兼容范围、兼容期与下线策略。
- 审批规则匹配阶段必须校验审批人有效性（用户存在且可用）；审批人已删除/失效的规则不得命中并创建审批单。
- 当候选规则因审批人失效全部不可用时，必须阻断本次业务写入并返回明确错误，不得按“未命中规则”直通执行。
- 审批任务创建必须执行“资源级互斥校验”：以 `moduleCode + resourceId + status in (pending,in_progress)` 作为唯一互斥键，不区分 `operationCode`。
- 命中资源级互斥时必须阻断并返回明确错误，不得因 `operationCode` 不同而放行（例如 `change` 与 `delete` 并发提单）。

名称唯一性约束（审批规则）：

- 规则名称字段：`ruleName`（DB: `t_approval_rule.rule_name`）。
- 默认规则：全局唯一，不区分启用/禁用状态。
- 新增规则：若 `ruleName` 已存在，返回参数错误并提示“规则名称已存在”。
- 变更规则：若修改后的 `ruleName` 与其他规则重名（排除当前 `id`），返回参数错误并提示“规则名称已存在”。
- 删除或禁用规则不释放名称唯一性约束（仍按全局唯一判断）。
